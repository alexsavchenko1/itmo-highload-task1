# ITMO Highload — TASK1

Учебный стенд для измерения HTTP-нагрузки и автоматического построения панели мониторинга. В составе: два экземпляра приложения на Java 21 / Spring Boot 3.5.16, Prometheus, Grafana и два отдельных процесса Python — генератор дашборда и генератор нагрузки.

**Главная особенность:** панель Grafana создаётся по текущему списку HTTP-обработчиков приложения (`GET /handlers`), без вручную заданного перечня бизнес-маршрутов.

## Требования и запуск

Для запуска нужны Docker Desktop (или Docker Engine с Compose), Bash и `curl`. Для локальных тестов Python нужен Python 3.10 или новее. Устанавливать зависимости Python через `pip` не требуется.

```bash
# Из корня проекта, только при первом запуске:
cp -n .env.example .env
# Задайте GRAFANA_ADMIN_PASSWORD в .env.

# Собрать приложение, поднять весь стенд и проверить результат:
docker compose up --build -d
bash check-stage4.sh
```

Переменные `.env` задают учётные данные Grafana и параметры нагрузки; `.env.example` — шаблон без рабочего пароля. **Не добавляйте `.env` в Git.** Повторный `docker compose up --build -d` не требует предварительного удаления контейнеров.

Проверка состояния:

```bash
docker compose ps -a
```

Ожидается: `app-1`, `app-2` и `grafana` — `healthy`; `prometheus` и `load-generator` — работают; `dashboard-generator` — завершился с кодом `0`. Последний запускается один раз, поэтому его завершение — нормальное поведение.

## Архитектура

| Компонент | Назначение |
| --- | --- |
| `app-1` | Java CRUD-сервис, `pod-1` / `dc-a`, порт хоста `8080` |
| `app-2` | Второй экземпляр того же приложения, `pod-2` / `dc-b`, порт хоста `8081` |
| `prometheus` | Каждые 5 секунд собирает метрики обоих приложений; хранит временные ряды |
| `grafana` | Показывает графики; источник Prometheus настраивается автоматически |
| `dashboard-generator` | Получает `/handlers`, строит запросы PromQL и создаёт дашборд через API Grafana |
| `load-generator` | После успешного создания дашборда постоянно отправляет запросы обоим приложениям |

Экземпляры Java работают в **разных контейнерах и JVM**. Каждый хранит записи в собственном `ConcurrentHashMap`; общей базы данных нет. Внутри контейнеров оба приложения слушают порт `8080`, снаружи доступны по `8080` и `8081` соответственно.

Docker Compose проверяет готовность приложений и Grafana через HTTP. Генератор нагрузки запускается после успешного завершения генератора дашборда.

## HTTP-интерфейс

| Метод и путь | Назначение |
| --- | --- |
| `POST /items` | Создать запись; успешный ответ `201` |
| `GET /items/{id}` | Получить запись; отсутствующий идентификатор — `404` |
| `PUT /items/{id}` | Изменить запись |
| `GET /health` | Проверка доступности Java-приложения |
| `GET /handlers` | Список зарегистрированных HTTP-обработчиков |
| `GET /metrics` | Метрики в формате Prometheus |

Для `POST` и `PUT` имя записи не может быть пустым: некорректное тело запроса приводит к `400`. В демонстрационном режиме заголовок `X-Demo-Error: 500` на `POST /items` позволяет намеренно получить `500` для проверки мониторинга.

## Метрики и дашборд

`HttpMetricsFilter` измеряет число завершённых запросов и время их выполнения. Метрики имеют метки `pod`, `dc`, `method`, `route`, `status`. Путь нормализуется по шаблону обработчика (`/items/{id}`), а не по конкретному идентификатору записи.

Служебные пути `/health`, `/metrics`, `/handlers`, `/error` исключены из бизнес-метрик, поэтому опрос Prometheus не увеличивает показанный бизнес-RPS.

Экспортируемые метрики:

- `app_http_requests_total` — счётчик HTTP-запросов;
- `app_http_request_duration_seconds_bucket` — корзины гистограммы длительности запросов.

На каждый найденный бизнес-обработчик генератор создаёт три графика: **задержка p50/p95/p99**, **RPS** и **ошибки 4xx/5xx**. Сейчас обнаруживаются три обработчика (`POST`, `GET`, `PUT`) и строятся девять графиков. При добавлении нового бизнес-маршрута и повторной генерации количество панелей увеличится автоматически.

В дашборде доступны фильтры по `dc` и `pod` с множественным выбором. В конфигурации дашборда установлено `editable: false`.

Пример скорости запросов:

```promql
sum(rate(app_http_requests_total{job="items"}[1m]))
```

Пример общего p95 по двум экземплярам:

```promql
histogram_quantile(
  0.95,
  sum by (le) (
    rate(app_http_request_duration_seconds_bucket{job="items"}[1m])
  )
)
```

Для объединённого p95 сначала суммируются скорости роста корзин с одинаковой границей `le`, затем вычисляется квантиль. На самом дашборде дополнительно используются фильтры по методу, маршруту, `dc` и `pod`.

## Генератор нагрузки

`tools/load_generator.py` использует стандартную библиотеку Python и отправляет запросы к двум экземплярам. **Заданный RPS — суммарный для обоих приложений**, а не для каждого отдельно.

По умолчанию нагрузка линейно растёт от **3 до 40 запросов/с за 120 секунд**, затем поддерживается на целевом уровне. Генератор выполняет `POST`, `GET`, `PUT`, хранит идентификаторы записей отдельно для каждого экземпляра и раз в 10 секунд выводит статистику в журнал.

Из каждых 100 запланированных запросов четыре намеренно ошибочные: две ошибки `404` и две `500`, по одной каждого типа на экземпляр (**4%**). Ошибки `400` проверяются отдельно проверочными сценариями и не создаются плановым генератором нагрузки. Фактическая скорость обработки может отличаться от целевой из-за ресурсов машины и задержек сети.

Параметры в `.env`:

```dotenv
LOAD_START_RPS=3
LOAD_TARGET_RPS=40
LOAD_RAMP_SECONDS=120
```

## Проверки

После запуска контейнеров:

```bash
bash check-stage2.sh                     # CRUD и коды HTTP для app-1
bash check-stage3.sh                     # оба экземпляра, Prometheus, источник Grafana
bash check-stage4.sh                     # дашборд, запросы PromQL, непрерывная нагрузка
python3 -m unittest discover -s tests -v # тесты генераторов и HTTP-интеграции
```

При сборке Java-образа Dockerfile выполняет `mvn verify`, включая тесты Java.

Для диагностики:

```bash
docker compose ps -a
docker compose logs --tail=100 dashboard-generator
docker compose logs --tail=50 load-generator
docker compose logs --tail=100 app-1
```

Если `dashboard-generator` завершился с ошибкой, проверьте его журнал и состояние приложений и Grafana. Повторная успешная публикация заменяет дашборд с тем же UID, не создавая копий.

## Демонстрация и остановка

Для демонстрации покажите состояние контейнеров, `/handlers`, `/metrics`, две цели `UP` в Prometheus, девять автоматически созданных графиков с фильтрами `dc` / `pod`, статистику генератора нагрузки и успешный `check-stage4.sh`.

Ссылка на запись демонстрации и запрос на включение изменений (PR) оформляются в соответствии с требованиями курса.

Остановить стенд без удаления данных Prometheus и Grafana:

```bash
docker compose down
```

**Не добавляйте `-v`, если хотите сохранить данные в томах Docker.**
